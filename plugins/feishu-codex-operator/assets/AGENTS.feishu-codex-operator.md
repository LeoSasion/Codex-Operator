## Feishu Operator runtime safety

### Authority and ownership

- Managed Web terminal 408/409/429/5xx causes use a non-retrying HTTP 400
  envelope with the original cause_http_status, fixed reason and partial-tool
  evidence intact. Only a bound Web service's validated bounded 400 may become
  a WebSocket error event; never convert native or other upstream failures or
  invent successful output. Keep authentication and capacity 413 boundaries.
  Independent Web providers keep both native retry settings at zero. A generic
  413 through the global native provider can still retry; do not re-enable global
  routing after native recovery on the strength of terminal-400 tests. Size
  diagnostics retain only fixed scope and bounds, never request content. Preserve
  original failed turns, histories, attachments and all capacity limits.

- Global activation may retain one exact leading, wholly commented legacy
  three-line Operator loopback block as inert bytes. Never delete or normalize
  it; active, incomplete, duplicate or unknown marker blocks remain conflicts.
  Cold-launch arming performs read-only config compatibility checks before
  saving intent; activation rechecks after recovery/health I/O. A failed intent
  remains terminal and retained for explicit reviewed maintenance, never reset
  or replayed automatically. Fixed local failure codes must survive redaction.

- Explicit reviewed legacy shortcut migration owns only the two current-user
  named extension shortcuts in a separate entry-only journal. Bind the preview,
  historical receipt, exact old launcher, current bytes and source/workflow
  fingerprints. Retain migration-time originals and missing-file state before
  writes; do not fabricate project/runtime/rule/Hook first-install ownership.
  Existing or uncertain transactions never retry automatically. Restoration
  checks current shortcuts, build and backups, preserves later edits, and keeps
  a native-only launcher for pins. Global teardown requires separate entry
  restoration first; legacy runtime ownership remains explicitly unresolved.
  Migration neither activates routing nor proves cold launch/Desktop acceptance.

- A legacy runtime cutover may explicitly bind one completed dead-Web recovery
  receipt when the manager reports configured with no current instance. Validate
  the selected receipt, retained originals, archived marker and complete recovery
  history, then recheck current profile/source and absent processes and listener.
  Keep the ordinary stopped-service path unchanged. This is separate evidence of
  absence, never a clean-stop claim or first-install ownership; do not manufacture
  a stopped record, start services to satisfy maintenance, or replay old requests.

- An owner-requested saved Web cold-launch plan binds exact source/profile,
  Python, workflow and dedicated empty registry identities. Preparation/status
  never start services or change native settings. Explicit service-start may
  prepare detached background services for acceptance, with no model request.
  Reuse only the exact process birth and source-bound router; uncertain launches
  stay terminal, and never recover or replay implicitly. Explicit router-stop
  requires a deactivated entry and server-confirmed request-free state, then
  process exit and an exclusively reservable port before marking stopped.
  The reviewed schema-v2 Web startup workflow prepares services, then the
  Operator desktop entry opens the official application. A separate owner-
  requested arm-entry retains original configuration and prepares recovery;
  only a later verified cold launch may activate its digest-bound unchanged
  config once. A failed/uncertain activation is never retried automatically.
  Existing running Desktop opens normally; it is never killed or restarted.
  Activation, model catalog refresh and live main-window acceptance remain
  distinct. A crash/reboot with uncertain service records still needs review.
  Explicit disarm retains the cancelled activation record without changing
  routing or services. Uninstall must first reject an active dedicated Web
  route, uncertain router, pending activation or running saved Web service;
  never archive its interpreter by checking only the legacy router port.
  Check an independently saved Web service even without a cold-launch plan;
  malformed or uncertain service records must stop teardown before writes.

- Local indexed-request section-capacity rejection is a typed preflight result.
  Return a distinct non-retryable 413 before browser submission, without truncating
  input or changing 48 KiB/24-page/40-read bounds. Preserve the existing idle
  browser and completed-page inspection only when no request packet was created.
  Keep the rejected native turn consumed; a different new request may use the
  same idle worker. Generic browser error text cannot claim this classification.

- Explicit mcp_context_records_v3 context pages preserve complete non-input fields
  and every ordered input record as structured data. Only oversized individual
  records use indexed JSON fragments; retain all roles, content parts, metadata,
  absent/scalar/array distinctions and exact values. Preserve 48 KiB replies,
  24 context pages, 40 single-use reads and complete context/schema gates. It adds
  no authority, history filtering, permission, inferred intent, execution or retry.
  Reading all pages does not establish model comprehension or correct task choice.
  Native test acceptance must compare the submitted user request with actual tool
  arguments and outputs; a successful command for an old request is still failure.


- Dated Web model catalogs preserve exact generation and effort selections. GPT-5.6
  and GPT-6 regular entries expose only observed Instant/Medium/High/Extra high;
  Pro is a separate entry whose fixed native max means the Web Pro position,

  range and explicit generation header before dispatch; Latest alone is not
  identity proof. Keep one shared browser/admission/consumed-turn ledger and
  exact per-request completion checks across models. Publish a complete bound
  catalog atomically without changing native defaults or bypassing recovery.
  An unbound starting record may be explicitly retired only when its original
  stopped snapshot shows zero requests, its parent and observed session PID are
  absent, exact dependencies and tunnel marker are absent, and the listener port
  is exclusively reservable. Retain originals and uncertainty; never fabricate
  worker ownership, auto-reset, launch or replay during this maintenance.

### Final Callback routing

- Before queueing, the Operator opens one durable callback route for a public,
  deterministic 32-hex `request_id` bound locally to the Feishu event and
  exact responder task.
- The Responder receives the user request plus only necessary attachment paths,
  the `request_id`, and a short instruction to call
  `submit_final_callback(request_id, final_answer)`.
- `request_id` is correlation data, not a secret, token, capability,
  authentication mechanism, or caller/turn attestation. Do not describe it as
  stronger proof.
- The Final Callback MCP server exposes only `submit_final_callback`. It must
  not expose claim, arm, finish, failure, catalog, task-control, or transcript
  tools.
- The first exact non-empty callback for an open request wins. An identical
  duplicate converges; conflicting, unknown, closed, oversized, or invalid
  submissions are rejected. Preserve the final answer as an exact Unicode
  string through delivery.
- Native assistant output, task reads, logs, databases, rollout files, UI, OCR,
  clipboard, and temporary files are never final-answer transports.
