# 项目文件复盘与清理

适用于 Codex-Operator 的开发工作区。清理释放的是可重建产物的空间，不改变功能验收结论，也不代替升级、恢复或卸载。

本项目的开发经验继续归入本文及对应功能的既有 Markdown；插件现有 Skill 负责导航。所有者未明确要求时，不因“沉淀经验”新建独立 skill，也不复制一套开发工作流。Codex 升级专项的方法与案例维护在[升级检查流程](upgrade-checklist.md)，验收事实留在[发布验收记录](release-audit.md)，完整私人原记录继续在隔离区保留。

## 架构调整后应保留的经验

1. **源码、安装、实机分别核验。** 规范源码只有 `plugins/feishu-codex-operator`。源码修复和单元测试通过，不代表已运行的安装包含修复；安装清单一致也不代表真实消息完成闭环。Channels 应核对同一条消息的任务 UUID、实际模型、工具执行、Final Callback 和对应回复。
2. **界面列表不等于任务身份。** 标题只作显示，绑定使用准确 UUID。原生列表出现空摘要或漏项时，不能因此重建、改绑或重放；只使用已实现的准确身份核验。额度检查应在自动创建任务和排队之前完成。
3. **先观察，再请用户操作。** 保存登录与连接应复用。只有准确当前页面显示登录或验证控件才请求协助；旧错误、辅助标记、窗口标题和“已打开”回执都不充分。页面未能观察就记录未确认。
4. **传输成功不等于业务成功。** HTTP 200、隧道计数、零工具调用和助手口头说明，均不能单独证明执行结果或云端拒绝原因。成功必须核对当前用户请求、实际工具参数和结果；执行了历史请求也算失败。网络失败、容量拒绝、权限拒绝与协议错误分别保留，不重放旧请求。
5. **功能边界不能用验收摘要抹平。** 独立 Web provider 的 CLI 读写、测试、搜索、历史与取消复用，不等于主窗口菜单或同任务模型切换已验收。Channels 新用户自动建任务也须独立验证，不能用既有账号闭环替代。
6. **运行路径比目录名可靠。** 临时目录可能实际保存正在使用的 Electron、Python 或浏览器资料；源码、设置及程序还可能绑定准确路径与摘要。卸载预检须覆盖独立 Web 服务，不能只检查旧路由端口或某一个启动计划。
7. **保留失败与原件，去掉重复载荷。** 失败日志、回执、夹具、版本和摘要是经验依据；缓存和重复解压内容不是。保留精确 ZIP 后可按逐文件摘要删除相同解压副本；相同测试程序可保留一份并记录其余路径的对应关系。恢复事务的原件不能用“另一份看起来一样的文件”替代。
8. **维护入口复用同一解释器选择。** Windows 只有 `py.exe` 而没有 `python.exe` 时，用户任务管理、卸载预览和发布审计原先会在调用前失败；这些入口现在使用只读、有界的 `Get-OperatorPython`，而 MCP 的 `python.exe` 就绪要求仍单独核验。隔离回归见 `test_user_task_status_reaches_helper_without_python_on_path`、`test_maintenance_entries_use_discovered_python_without_python_command` 和 `test_release_audit_works_with_only_python_launcher_on_path`。

功能状态按[发布验收记录](release-audit.md)、[核心验收](core-recovery-20260921.md)和[原生对话改进计划](../../models/web/docs/native-conversation-plan.md)中的准确版本、入口及日期判断；清理不把历史待验项改判为通过。

## 升级质检后应保留的开发经验

以下经验来自 2026-10-15 的修复与失败复现，具体边界和受影响测试见[升级回归检查点](upgrade-checklist.md#6-已复现的升级回归检查点)。

1. **身份要验证实际对象。** Hook 的脚本路径子串会误认相似文件或其他脚本的普通参数；入口原始字节相同也不能替代 Windows 文件身份。未知参数、身份或原件保持阻断，不控制无关进程，也不制造初装归属。
2. **私有校验通过不代表公开操作可达。** 严格 validator 已认可的旧回滚，仍可能被公开入口的通用 pending 护栏提前拒绝。维护测试要覆盖公开分派与完整恢复链，保留未知事务的拒绝。
3. **负向夹具必须证明错误真的发生。** 来源注入应自检命中次数与摘要差异；未命中不能算防护成立。门禁收紧后更新原合法样本，使凭据、allowlist、原件及字节断言仍能到达，不削弱原断言。
4. **临时目录不隔离全部资源。** 固定端口及其传递依赖夹具需要串行；Windows 无控制台子进程还需显式固定 JSON 发端 UTF-8，并保留严格解码及中文、非 BMP 字符检查。不用重试、放宽产品端口门或替换错误字符来掩盖失败。
5. **元数据也有自己的保护门。** 安装器版本应从规范定义读取并在写入前核对清单，不能漏同步硬编码。原生缓存的 `fetched_at`、`etag` 改变仍是保护漂移；模型记录未变不能抹去原失败，也不能无证据归因或恢复活跃缓存。
6. **总结回到已有入口。** 一般开发教训写在本文，专项细节写在对应功能文档，Skill 只链接它们。私有日志、摘要、失败回执与归档原件留在本机，不把它们整份搬进公开经验文档。

2026-10-16 继续维护时确认了三项边界：子进程退出不代表 stdout 已排空，队列暂空也不代表 EOF；安装应在打开写入事务前检查完整计划，再在逐项写入前重查；协议转换可能扩展数据，输入未超限不能代替对实际下游序列化字节的校验。对应回归和限制继续维护在[升级检查流程](upgrade-checklist.md#7-断线安装与转换输出的边界回归)，不另建经验文件。

2026-10-17 的参考研究先固定提交与符号，再比对本地覆盖并复现缺口。只借鉴必要机制：成功完成标记与连接 EOF 分别判断，当前已收到的整块数据仍须先完整校验；文件发现的异常边界应包含排序时最后一次 metadata 读取；HTTP 多值头须逐行检查，不能只取第一值。当前 CLI schema 的新增不透明字段也须检查所有已有 item 类型，不能只看原消息分支，具体回归方法留在[升级检查流程](upgrade-checklist.md)。采用、已有覆盖与待议建议分列在[现有吸纳记录](codexplusplus-adoption.md)，不把上游重试、历史改写或新界面一并带入。

## 冻结验收与部署

以下方法来自 2026-10-28 的分层诊断、取消、冷启动和插件交付；具体案例继续保留在相应功能文档和私有回执中。

1. **按证据所在层判断。** 保存的连接/浏览器快照、当前认证本地健康、模型目录及实际工具结果分列。停止或未绑定实例也可保留有界阶段信息，但快照不能证明当前进程、登录或连接，更不能补成 worker 归属或取消失败事务。诊断只输出固定枚举、布尔及有界计数，状态读取不新增探测、模型请求或恢复。
2. **把期限和取消对象对准。** 整个 Web 回合、单次隧道响应和原生工具各有期限；先核对当前版本与合同，再用真实 loopback 提前断开验证调用取消、迟到结果拒绝及原回合不可重放。外部项目的 60 秒限制不是本机事实。合成 App Server 用全新私有 home、never/read-only 和本地模型/MCP，核对 request ID 类型、请求先于取消、interrupted 终态及同进程的不同新调用；它不代替 Desktop Stop 或真实 Web。Windows SQLite home 使用短路径并保留用例映射；RPC 遇 EOF 立即记录失败。夹具的语法、路径和到达前失败单列，不改短参数、扩大期限或删除历史求通过。
3. **回环失败先核对是否到达本地。** CLI 或自定义启动出现 502 时，先用无账号、无模型的合成请求区分代理路径与本地服务。确认排除项缺失后，只在该子进程补充 localhost、IPv4、IPv6 的 `NO_PROXY`，并保留继承的代理及原排除项；核验父环境未变。修复后复测原失败路径，保留旧失败，不改生产路由、权限或重试策略。冷启动的实机边界见[入口验收](../../models/common/docs/mode-entry-window.md)。
4. **先冻结，再运行所需检查。** 版本、公开文档及其审阅摘要应在完整回归前定稿。记录源码、CLI、运行环境与测试结果的绑定，期间不改源码；中断或未完成的测试不能算通过。固定诊断码从产生位置核对，近似名称按未知值脱敏。纯文档和缓存清理使用本文末尾的定向检查，不重复完整业务验收。
5. **按预期变更核对配置事务。** 官方 Marketplace 注册和安装会改变相关注册项，也可能自动启用插件。先明确允许变化的准确字段，再核对其余配置及保存的插件偏好；不能用“整个配置零变化”拒绝正常的注册变更，也不能为恢复一个开关回滚整个配置。步骤停下后检查已完成的准确边界，保留失败记录，只完成尚未执行且已核对的步骤。方法见[Windows 配置事务](../../models/common/docs/windows-config-transaction.md)。
6. **把动态状态与自己的交付分开。** 验收期间原生配置、模型缓存时间、etag 或目录记录的字节漂移仍保留原件及失败保护门；路由相同、原模型仍在也不能改判或无证据归因。保留用户后续设置，不追逐不断刷新的缓存。插件升级后的旧缓存目录可能由 CLI 清除；旧快照或 ZIP 可恢复原字节，与原目录仍在是两个事实，须分别实查。
7. **核对实际交付字节。** 源码、运行时、Marketplace 快照、已安装插件、发布 ZIP、下载回读及实机行为分别报告。ZIP 与安装须逐文件比对，不能只比较版本号或一份安装器自报；运行时没变时，不为文档或启动器修复虚增运行时版本。准确范围见[发布验收记录](release-audit.md)。

## 按用途决定去留

运行时引用必须纳入目录清理判断。2026-10-28 的后续验收发现，已保存的 Web 设置仍引用另一个工作区 `gpttest/.operator-tools` 下的 tunnel-client、固定连接密钥和绑定文件，而三个原路径均已不存在。没有活动进程不代表目录没有冷启动依赖。清理前核对保存的设置、profile、部署回执和准确原件；密钥或绑定丢失时保留原失败，先定位备份或由所有者重新建立连接，不从日志拼接凭据、不重造绑定或重放旧请求。旧路径失效不证明插件源码有错，也不允许绕过停机迁移门槛。

| 文件用途 | 处理方式 |
| --- | --- |
| 规范源码、测试、示例、skill、公开文档、许可证及发布清单 | 保留；按功能目录维护，避免重复源码 |
| 正在使用或保存配置仍引用的程序、依赖、浏览器资料 | 原位保留；确需迁移时另做服务维护和登记更新 |
| 消息、任务与回调数据库，凭据，原生配置及历史 | 保留；不属于工作区垃圾 |
| 快捷方式、Hook、路由恢复的原始文件与事务记录 | 保留完整字节、路径和缺失状态；完成状态本身不足以授权删除 |
| 成功、失败、不确定的测试日志、请求证据、夹具、迁移映射 | 私有保留；提炼结论时链接原证据，不改写旧结果 |
| 未运行参考项目的安装依赖、可核对的缓存、重复解压目录 | 确认无活动或保存引用后可清理；保留源码、锁文件、固定提交与许可 |
| 多份完全相同的测试程序 | 保留一份可定位的精确版本，记录摘要与去重关系；不代替任何恢复原件 |
| 不明用途的旧文件、独有修改、链接目录 | 继续留在所属功能的隔离区，注明阻碍判断的事实 |

`.gitignore`、`.tmp`、`_quarantine` 和文件日期都不是删除依据。根 `.git`、插件缓存和工作区外的文件不纳入普通项目清理。

链接也属于引用：除检查目标自身和祖先外，还要核对现存 junction/symlink 的准确目标，不能删掉另一个目录仍链接使用的依赖。名称和大小相同的程序也可能字节不同；只有摘要相同且用途明确的离线测试副本可以去重。保留逐文件来源映射，清理不会让旧用例自动恢复可运行，也不允许自动重建或重放旧验收。

## 一次清理的操作顺序

1. 记录 Git 已有改动，盘点整个工作区的文件数量、大小和链接；不跟随 junction、symlink 或其他 reparse point。先读目标目录适用的项目指令。
2. 只读核对准确进程及出生身份、保存设置、Web 服务登记、启动与恢复记录。保存引用仍有效但程序暂未运行，也属于在用依赖。
3. 将每个候选的理由、绝对位置、大小、修改时间和 SHA-256 写入私有清单；关联需保留的日志、源码、ZIP、同内容程序或锁文件。重复解压目录须逐文件与保留 ZIP 核对，额外或不同文件不删除。
4. 删除前再次解析路径，确认目标及所有祖先都在指定工作区内且没有链接；重查进程引用、文件摘要和完整目录清单。出现新文件、变化、占用或身份不明就停下该项，不扩大范围或自动重试。
5. 用 `-LiteralPath` 精确删除已核对文件，再移除已核对且空的目录。不要对整个工作区、`.tmp` 或 `.codex` 运行通配清理，也不要使用跨 shell 拼接的删除命令。
6. 写入实际删除回执；失败保留为失败，不能用计划数量当完成数量。执行回执应独占创建，已有或部分执行记录先审查，不直接重跑脚本。复核保护文件摘要、保存配置有效性和准确服务状态。不发真实模型请求或消息来探测清理效果。
7. 同步相关隔离区说明，保留历史清单本身。纯文档与缓存清理执行发布清单、链接、语法和敏感内容检查；无需因此启动完整业务测试或重启服务。

清单、逐文件摘要和含本机路径的报告保存在私有目录；公开文档只保留方法和经审阅的结论。报告文件逻辑大小与实际磁盘空闲变化时分开计量，硬链接、压缩及并行写入都会影响后者。

## 发布时避免把开发现场带出去

公开源文件按 `assets/release-inventory.json` 收集。五份常用公开文档只在原位维护；发布构建核对其中的 `reviewed_document_sha256`（仅计算摘要时统一 CRLF/LF），并再次检查敏感内容，打包仍保留原字节。修改这些文档后须审阅完整新内容，再更新对应摘要；摘要通过不代替人工检查。

更完整的旧开发记录只在 `_quarantine/private-docs-*` 作为私有历史保留，不参与发布。普通 Git 暂存不会执行发布筛查；不得直接 `git add -A` 后假定本机路径、身份或运行记录会被排除。先审阅准确 staged 字节及发布清单中的所有其他文档，不把历史记录中带日期的“当前”当作新状态。

整理这类旧工作区时，先将长记录完整归入所属功能的 `_quarantine/private-docs-YYYYMMDD/`，留下原路径、原件摘要和公开版本的准确 Git 提交，再把主文档统一为已审阅摘要。调查历史问题时按归档清单回查原记录；原文中带日期的“当前”“未发布”等表述属于当时状态。

源码推送、源码预览包、正式 Release 和本机安装是四个独立结果。旧候选 ZIP 留存仅供溯源，不作为重新发布的输入；有新授权时从当时已审阅的源文件重新构建并检查。
