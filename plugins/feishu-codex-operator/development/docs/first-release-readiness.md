# 首发范围与发布验收

更新：2026-10-06。所有者已同意先收敛到 Windows、飞书和少量实测模型，Web 保持实验状态。本文落实该范围并列出发布门槛；不表示已正式发布，也不将历史成功升级为当前版本的验收通过。

插件版本为 `1.2.0-preview.1`。版本同步、安装文件一致、源码回归、实际 Desktop 验收、真实飞书收发分别记录。最终发布需要冻结具体源码、插件包、运行时、官方 Desktop/CLI 版本以及所选端点契约；每项结果只能用于自己的准确绑定。

## 第二用户验收流程

这是待执行的实机清单，不是自动给其他账号授权，也不发送消息或创建任务。执行时每个案例使用不同新输入和唯一标记，先明确账号与授权范围；必要的登录、审批与真实用户消息由本人操作。

1. **确定新账号。** 所有者提供一个获准、与现有所有者不同的真实飞书账号。按准确身份核验 sender；姓名相同或联系人解析回到所有者不算第二账号。先检查未已有绑定，不按显示名或项目标题认领任务。
2. **核对首次配置与授权。** 在首次接入前复核实际安装与准入状态。访问申请、所有者批准准入、项目/默认任务授权、持续自动建任务授权分别核对；申请已收件不等于获准。固定转交方式由用户明确选择 Luna/low 或本地 Beeper，复用已保存明确选择。本地 Beeper 的原生接入未验证时如实记录，不静默替换方式。`/init` 只查看原生目录并经确认选择准确已有任务，不因此创建业务任务或取得审批权限；已获准自动接入不强制再用 `/init`。详见[命令边界](../../channels/feishu/docs/feishu-command-ux.md)。
3. **第一次业务消息。** 新用户从自己的私聊发送一个带唯一标记的简单需求。核对 durable inbox、准确 scope-to-task UUID、新原生任务的实际输入和终态、一次对应回复；固定 Beeper 不得充当业务 Responder。
4. **同范围续聊。** 发送另一个新输入引用前一项结果。确认同一准确任务、完整上下文与正确结果；验证未错误复用所有者任务，也没有复制或覆盖历史。
5. **附件往返。** 使用新准备的文本文件/图片检查实际接收内容；独立新任务产出附件时核验收到的文件字节或图像内容。工具/回调成功状态不能代替本人收到相应附件。
6. **范围与权限。** 对获准群聊和话题各用新标记核对独立 scope；未授权账号的独立请求不得自动创建业务绑定或执行。业务任务审批仍由原生 Desktop 决定，不从飞书登记推导文件操作批准。
7. **恢复与重复事件。** 先确认请求已终态、队列和回调为空，再按既有显式流程停止/恢复。发送不同的新输入检查原任务接续；对选定的已消费事件作受控去重检查时，不再次投递为新业务、不重放失败输入，核对执行与回复计数没有增加。
8. **收尾与回执。** 保留实际成功、失败、未执行和缺少环境的状态，准确写下每项 task/turn、scope、版本、UTC 时间及原件摘要。测试任务按准确 UUID 管理，不能用标题批量删除用户会话；归档也保留完整历史。最后确认正常停止/恢复后的状态，不把安装完成写成全门通过。

用户首次接入流程已有[实现说明](../../channels/feishu/docs/automatic-task-provisioning.md)。公共报告只保留支持范围、结果与限制；账号、聊天、密钥及完整原始回执留在私有验收材料中。
