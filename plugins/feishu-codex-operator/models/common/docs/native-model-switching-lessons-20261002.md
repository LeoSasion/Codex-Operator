记录日期：2026-10-02。所有者要求先保存走不通的教训，再共同讨论需求方向调整。
本页记录已知结果与决策教训，不宣布新的实现方案，也不授权恢复旧路由或部署候选。
“未打通”均指下述版本、实现和证据范围，不等于技术上永远不可能。

## 后续需求决定（2026-10-02）

进一步收敛：所有者明确认为同聊跨 provider 切换不值得继续攻克，本轮移出目标。
拓展中的自定义型号仍在统一 provider 内切换；若原生 GPT 经过路由影响正常使用，
允许考虑拓展列表不保留 GPT。此项是条件性备选，不是移除官方原生模型的授权或已完成
结论，也不能把“隐形思考”写成已证实根因。旧往返成功、压缩和历史失败均继续保留。

最新补充：入口改为左“原生”、右“拓展”的可视小窗；所有官方普通入口均应保持原生
设置和直连。该要求排除了原样复用旧共享配置激活。所有者对分开会话列表持条件性倾向，
要求先谨慎讨论；未授权复制登录、迁移历史或创建新的隔离环境。
当前仅完成[启动选择窗预览](mode-entry-window.md)，后端接入与隔离验收仍未完成。

复盘完成后，所有者接受为原生菜单和同聊切换而让原生请求经过必要的本机统一路由，
条件是实际验证原生功能稳定性；希望追求稳定时仍能从原生入口使用官方直连。
该答复撤销了“不得考虑原生转发”的推定，不撤销现有安全边界或授权重放旧计划。
当前是方向讨论与实现来源核对，尚未切换真实配置或重新启用路由。

两个快捷方式当前共享应用与 Codex home，不是天然隔离环境。原生入口须实际完成准确
配置恢复，并核验应用/会话采用的提供方，不能由入口名称推出“完全不受拓展模式影响”。
恢复还需覆盖自定义聊天的重开，避免再次删除其仍引用的 provider 定义；历史兼容问题
不会仅因换入口而消失。是否需要正常退出，以及原生语音/辅助功能，均按实测说明。

只读 Git 核对：当前 `main` 的 HEAD 为 `2136156`（2026-09-28）；统一冷启动、统一
Desktop 接入等关键源码仍是未提交文件，9 月 30 日至 10 月 1 日的工作不能靠回退这一
提交完整重建。优先参考旧提交、当前 canonical 源码和保留的精确验收/构建材料，逐项
复用统一 provider 的菜单与路由能力，保留后续恢复、编码和历史检查修复。
不执行整仓 reset/checkout，不用安装缓存覆盖源码，不直接恢复已消费的配置/服务计划。
如进入实施，先保存当前完整工作状态，再生成新的可核验候选；本轮未提交或部署代码。

## 需求解释上的教训

- 核心体验是从 **Codex 原生对话框的模型列表**选择模型，由同一个 Desktop 持有聊天、
  上下文、权限和工具。所有者后来明确否定应用外的启动选择器作为交付方案；较早接受
  “拓展入口”的答复不能继续被解释为接受外部选模或频繁退出重开。
- “原生模型尽量不经过代理”是为了稳定性提出的偏好，不是无条件禁止所有转发。
  自定义模型可部分受限，也不代表可以牺牲原生菜单。先说明体验与稳定性的实际取舍，
  由所有者共同决定；不能把“优先直连”自行升级成压倒其他需求的硬约束。
- 所有者曾表示自定义模型约 75% 可用也可接受，这是对受限功能的容忍，不是已测成功率、
  自动重试许可或丢弃上下文许可。哪些功能可以受限须具体讨论。
- 从统一 provider 拆成独立 provider 的主要动机确实是保留原生官方直连。
  后续体验退化来自助手的实现与取舍，不能归因于所有者“要求太多”。

## 已走过的路径与停止重复尝试的条件

| 路径 | 确认的结果 | 教训与重新考虑的前提 |
| --- | --- | --- |
| 统一 provider 按型号转发 | 原生菜单曾显示 Native/Local/API/Web；同一任务的原生 → Web → 原生短文字接续通过 | 路由解决了逐回合换端点，但原生也经过本地路由；历史、压缩、容量/重试和辅助功能问题仍在。不能说“以前全不能用”，也不能说“所有模型随便切都通过”。重新选择此方向要单独评审，旧消费/失败/归档计划不可重放 |
| 官方直连 + 每个自定义模型独立 provider | 配置/profile/目录检查可通过；官方 CLI 的隔离重开恢复可以保留同一 UUID 并换端点 | 这不是运行中 Desktop 的逐回合切换。当前 CLI 0.159.2 的 `turn/start`、`thread/settings/update` 没有 `modelProvider`；start/resume/fork 的字段不能直接当作热切换能力。先证明真实会话绑定会更新，再扩展安装流程 |
| 外部启动选择器 + 冷启动入口 | 配对入口曾安装成功，Qwen 冷启动选择/配置也曾核对通过 | 用户已否定此交互；启动成功没有证明自定义模型能回答。不要继续完善此选择器或让用户反复重启来替代功能验收 |
| 同一 LM Studio 地址、每个型号一个 provider | 当前七个候选登记中，五个本地型号共用地址却分别使用 provider ID；候选按 ID 拒绝跨 provider 选择 | 人为拆分增加了切换障碍。若端点、鉴权与协议合同一致，可研究共用 provider、只改 model；同地址本身还不充分，型号能力和上下文窗口仍需分别保存。尚未实现或完成真实模型往返验收 |
| 原生菜单 JavaScript 接入候选 | Desktop 26.928.2636.0 私有副本匹配到菜单、新任务及已有任务检查接入点；静态语法和策略检查通过 | 未安装、未通过主窗口验收；不是官方插件 API。现有候选只为新任务绑定提供方，旧任务跨提供方被拒绝。不能把静态可补丁当作 Windows 包完整性、稳定性或可恢复部署证明 |

共用一个自定义路由器可让不同外部端点在一个 provider 下换型号；这本身仍不解决它与
独立官方 provider 之间的运行中切换。新讨论必须明确哪些切换组合是交付目标。

## 把不同故障分开记录

| 场景 | 已有证据 | 不能推出的结论 |
| --- | --- | --- |
| 2026-09-30 原生 → Web → 原生 | 同一真实 Desktop 任务经普通菜单/输入框连续三轮成功，并引用前轮答案 | 不证明所有 API/Local 型号、长历史、工具或语音通过；后来的失败也不能抹掉这次成功 |
| 原生历史 → Qwen3 0.6B | `opaque_cross_provider_context_not_supported`；后续只读复核找到切换回合的 `compacted` 记录及加密 compaction 项。型号登记窗口为 40,960，Desktop 有效窗口 38,912，先前原生为 258,400 | 这次有切换过程中压缩的证据，不应仅笼统称为“本地推理失败”；不能外推所有原生到第三方切换都会如此 |
| Gemma 首轮成功，继续第二轮 | 首轮普通文字回复通过；后续 remote compaction 报 `unsupported_history_item`，准确拒绝形状未捕获 | 不归因于某个确定历史字段，也不把首轮通过当成连续对话通过 |
| 旧 Local 聊天 → 原生 GPT-6.1 Sol | 新输入报 `array_above_max_length`，`input[4].content` 最大允许 0、实际 1；历史中存在公开 Local 推理内容 | 这是字段结构校验，不能仅按 token 超限处理。该推理项与错误索引的对应关系仍是推断；没有完整请求证据，不武断认定具体内部阶段或说“只在压缩时出错” |
| Qwen3.8 直连新聊天 | 已绑定 `operator_native_local_qwen38`，Responses 请求返回 502 | 事后本地端口无监听不能证明当时 502 的具体原因；不归为压缩或模型能力失败 |
| 上述 Qwen 聊天在恢复原生后重开 | 旧恢复投影移除了 provider 定义，聊天元数据仍引用它，出现 provider not found | 默认切回原生与删除仍被聊天引用的提供方是两件事。未来恢复设计须覆盖自定义聊天重开，不能只检查官方根配置。此修复尚未实施 |

因此有三类独立问题：**会话绑定哪个提供方、下一端点能否接受已有上下文、当前服务能否正常响应**。
换型号、换 provider、改全局默认、刷新菜单和恢复原生配置也不是同一个动作。

## “先压缩再切换”的结论边界

这是所有者提出的待验证方向，尚未实施，不能记为解决方案或被否定的路线。

- OpenAI 远程压缩会产生不透明的加密 compaction 项，当前第三方适配拒绝此类历史。
  因此“提前按一次压缩”不自动生成可跨提供方使用的文字上下文，可能仍保留同一障碍。
- Codex 客户端的文字摘要式压缩值得单独验证，尤其是第三方 → 原生；须核对实际输出与
  保留项，正常续聊是否完整，不能保证一次摘要消除所有不兼容数据。
- 压缩不改变会话 provider 绑定，也不修复缺失配置或服务 502。旧统一 provider 的
  名称/能力曾影响其下全部型号的压缩路径，不能为修自定义模型而悄悄改变原生行为。
- 仅由官方客户端按选定方案正常压缩；不手改历史、不解密或删除不支持的项、不伪造摘要、
  不把推理改成答案，也不重放旧失败。单个合成压缩通过不证明实机切换通过。

技术依据见[压缩合同](model-router.md#client-owned-compaction-2026-09-30)及
[OpenAI 压缩说明](https://developers.openai.com/api/docs/guides/compaction)。

## 验收与交接上的教训

1. 逐项区分配置加载、模型目录可见、真实主窗口可选、准确端点收到请求、正确回答、
   同聊连续使用/双向切换，以及工具、压缩、语音和重开。前一步成功不能替代后一步。
   拒绝边界测试通过，意味着正确保留了失败，不意味着那轮模型使用成功。
2. 先用明确版本和代表性新样例证明最关键的原生菜单/路由/续聊链路，再扩大入口和安装
   工作。不能把大量隔离测试、入口维护或源码匹配当作用户已可用。
3. “本次结果已保存”只表示结果已写入；倒数结束、窗口关闭和进程消失都不是更新完成。
   交接还需分别核验正常退出、实际写入、结果解析与应用重新打开。
4. 已发生过“安装写入成功，但中文 stdout 编码解析失败，未自动重开”。这类部分结果要
   通过独立只读核验判断，保留原失败；不能再跑安装、退役或归档来碰运气。
   公共 CLI 的 UTF-8 修复与真实主窗口功能是两个验收层次。
5. 后续测试尽量降低用户反复关闭/重开的成本；先把可独立验证的准备做完，再说明一次
   用户操作具体要验证什么。保留官方直连的当前可用状态，旧计划和证据不回放、不改判。

## 当前阶段与需求讨论入口

以下为复盘完成时的讨论清单；随后接受统一路由的决定见本页开头。未部署的原生菜单候选、
已安装但不满足体验的外部入口、已归档旧统一方案均保留各自状态；不因为本页自动启用、
拆除或迁移它们。下一轮先明确：

1. 原生菜单选模是既定要求；同一会话需支持哪些组合：自定义内部、原生到自定义、双向？
2. 已接受拓展模式必要转发、原生入口保留官方直连的目标；仍需核对共享配置和运行中
   会话如何切换，不能宣称当前 Desktop 已支持逐会话隔离两条路径。
3. 哪些限制可接受：只限制特定切换组合、由客户端先做文字压缩，还是其他明确范围？
   摘要的信息损失、工具历史兼容和额外操作成本都要说清，不能默默替用户决定。
