# 原生 Codex 对话改进计划

更新：2026-09-28。本页只保留当前计划；重复的逐轮验收已合并到[历史记录](native-web-history-20260924.md)。执行前读[当前项目记忆](native-web-experience.md)，原始通过、失败和未确认记录保留，不能据后续成功改判。

## 目标与参考

所有者要求原生 Codex 对话更流畅、少点击、少配置、少弹辅助窗口。首要参考、四个独立的冷置参考及其身份/许可边界集中记录在[实现来源](web-background-sources.md)；仅有具体缺口才再查冷置项目。不开发另一套工作界面、浏览器伴随扩展产品、Goal/Loop 或多智能体编排。重大内部改造先说明收益、迁移/恢复和验收范围。

## 已落地的基础

| 能力 | 当前实现及证据 | 不包含的结论 |
| --- | --- | --- |
| 保存一次、准确复用 | `configure` 省略参数时只读校验已有设置；诊断区分访问、登记、程序与检查失败；实机重复复用未改保护文件或进程 | 不自动采用变更配置，不代表工具声明刷新已完成 |
| 隐藏页面准备 | 保存服务在接纳前尝试准备空白临时聊天；成功后消费时重新核验；准备过程零模型请求 | 近期有实例落到旧对话/非聊天页而未就绪；每个实例都要核对，不能因保存登录而默认可用 |

| 独立 provider 维护 | 只读识别 stale 代次；`desktop-rebind` 保留 provider 与原件；原生归档/恢复后，同一旧任务的新读取请求已走当前后台并返回准确结果 | 助手引导的空闲任务重载，不是自动热更新或跨 provider 切换 |
| Web 自有搜索 | Web provider 内适配已核对的可选 live hosted 声明；返回观察到的页面答案和引用 | 不关闭全局/项目搜索，不伪造 Codex 搜索调用，不保证所有查询正确 |
| 原生工具链 | 隔离 CLI 编码案例已通过；9 月 27 日新的原生任务实际完成读文件与回复，随后同任务的新温度样例完成两次配对调用、精确修改、五项测试及最终回复 | 温度案例显式要求先等读取结果再修改；不代表所有模型/工具、手动输入框或同任务切换已验收 |

## 接下来仍需证明的体验

### 1. 准确连接的工具声明维护

比较完整语义声明，包括名称、描述、输入/输出 schema 和风险标记；不能直接照搬只比较部分字段的上游摘要。声明未变时零刷新；变化时只维护准确 app，在空闲实例操作一次并读回结果。未知结果保留，不能再次点击或自动重试。

本地公开隧道的显式 `check_connection` 已改为按服务实际的 structured begin/call 模式核对完整 `tools/list`；隔离测试证实同一声明通过，以上五类字段任一变化均拒绝。这个检查只验证本机服务与公开端点的一致性，尚未读取 ChatGPT 已安装 app 的冻结快照，也未执行页面刷新。

2026-09-25 页面核对到准确的开发版“Operator 固定连接”，已有连接和“允许使用所有工具”；当前源码的完整隔离调用也成功投递。设置页提供“刷新工具”，但没有展示冻结声明供逐字段比较。本轮没有工具 schema 变更，因此未点击刷新；如将来声明变化，仍须完成快照比对和一次性刷新验收。

验收：隔离测试覆盖字段变化及未变复用，再检查当前页面真实刷新次数和结果。已有连接、授权和登录继续使用。此项仍待实现与验证，不因保存入口已复用而算完成。

### 2. 页面准备后的连续任务与停止体验

隐藏准备已实现，但近期启动页曾进入旧对话，仍须逐实例核验。2026-09-26 的新隔离原生 CLI 任务已用不同输入连续完成两轮，第二轮准确引用第一轮答案；当前 React 节点只剩一侧挂载时须证明其父节点属于当前页面，才能继续读取旧页并切换到新聊天。两轮接续使用隔离纯文本配置；保存的引用配置已恢复，并有一条新的原生 CLI 搜索请求完成上下文读取、来源校验和最终回复。早先那条引用样例要求网页不要使用 Operator，不能用来评估正常工具读取。保留已完成页的只读 `inspect`；`assist` 是空白聊天恢复，不用于保存现场。

2026-09-28，助手通过普通 Desktop 输入框在同一原生 Web 任务连续提交三个新样例：分别实际读取新文件，后两轮准确引用前轮标记；工具参数、零退出码、文件内容与最终回答逐一一致，耗时分别为 23.6、24.9、26.7 秒。全程沿用保存登录、固定连接和引用配置，没有辅助弹窗；停止操作后接纳新输入仍待主窗口实测。此前一条输入在 app 标记分隔处出现单字符公开表示差异并被拒绝，保持失败；新兼容只接受完整 app 链接和正文不变的单个空格/NBSP 投影，不放宽正文校验或重发。

验收：同一准确原生任务三轮新输入，逐轮核对当前需求、完整历史、工具与结果身份；正常路径无抢焦点/辅助弹窗。取消请求保持终态，不重放，只有经准确空闲核验后才接纳不同新输入。测量本地准备时间与上游生成时间分别报告。持续验证提示须实际观察后才请求用户操作；页面看不到就记录未确认。

早先多条原生样例执行只读命令后，因 250 项同身份内部工具定义改变而拒绝配对结果。9 月 27 日的新字段诊断确认另一条样例仅有 24 项叶子工具说明改变，参数、权限、身份与顺序未变。现在仅允许更新从未读取过的工具 schema 中的说明；目录已发布的首个读取 key 保持，完整新说明按原有边界重新分页，结果身份和历史全部校验后才原子发布。已读/部分已读定义及其他字段仍拒绝，具体规则见[项目记忆](native-web-experience.md)。新的原生只读任务在实际更新 250 项未读说明后完成结果和最终回复；同任务的独立温度案例也完成读改测。更新来源尚未确认，不能把这种兼容扩展为任意目录变化，旧失败保持原判。

与本机版本号对应的 [Codex 官方源码](https://github.com/openai/codex/tree/rust-v0.155.0-alpha.16.4) 表明，顶层工具声明[每步重建](https://github.com/openai/codex/blob/3853cf0c49daadcacaacceb2cbb732f512eaacdb/codex-rs/core/src/tools/spec_plan.rs#L532-L569)，同一 MCP binding 的工具定义由已建好的 spec 复用；`tool_search` 的延迟加载结果进入[输入历史](https://github.com/openai/codex/blob/3853cf0c49daadcacaacceb2cbb732f512eaacdb/codex-rs/core/src/tools/context.rs#L208-L245)，不能据此解释顶层声明改写。认证、环境或插件状态变化可能触发[绑定刷新](https://github.com/openai/codex/blob/3853cf0c49daadcacaacceb2cbb732f512eaacdb/codex-rs/core/src/session/mcp.rs#L175-L253)，但本例没有这类事件证据，公开源码也未证明与本机二进制字节完全相同。未读说明兼容来自实际字段和阅读状态校验，不依赖对生成原因的猜测。

2026-09-27 回查找到了 9 月 18 日真实 Desktop G1 的原始成功回执（两次命令、精确修改、五项测试）及目录整理前的 9 月 20 日发布源码。在本次修复前，该发布快照与工作区的 `_accept_result`、`WebModelProtocol.__init__` 语法树一致，工具适配器的函数和类也一致；它不是 G1 当时全部源码的逐字节证明，但排除了这几处逻辑在后续目录整理中被改写。原始证据与失败记录仍保留；参考比较见[实现来源](web-background-sources.md)，测试范围见[发布审计](../../../development/docs/release-audit.md)。

### 3. 原生任务入口与模型选择

当前基线是官方直连加独立 Web provider，专用 Web 任务由助手配置。CLI 0.155.0-alpha.16.3 的合成检查证明：新任务可绑定未列于主 `model/list` 的准确 Web provider；首轮落盘后新进程可恢复该绑定。新进程也能显式切换提供方；同进程已加载任务的恢复/设置更新探测仍把请求送到原提供方。因此菜单出现、配置返回成功和实际去向必须分别核对。

2026-09-27 已在 CLI 0.158.0-alpha.2.1 上修复旧任务缓存地址这一维护缺口：原生工具归档并恢复同一空闲任务后，全新的文件读取请求完成实际配对调用和准确最终回复，未重启 Desktop、改写全局配置或重建任务。恢复工具曾返回加载错误，但只读核验确认它已经解除归档；未重复恢复操作。具体操作与停止条件只维护在[任务重载](native-web-experience.md#reload-an-idle-web-task)。此结果不改变上述跨 provider 切换仍待验证的结论。

已有专用任务在助手任务工具转交下完成过文本接续；该转交不是普通输入框。9 月 28 日又完成了当前 Web-only 搜索配置下的主窗口打开、普通输入和三轮接续，详见上面的连续任务记录。下一步仍需分别验证停止与受支持的模型选择入口。不能为了跨 provider 切换自动重启 Desktop、改既有任务历史或恢复全局路由。

验收：新任务接入、同任务选择、实际请求去向、历史接续、读改测和原生审批各有准确证据。若原生接口仍不支持切换，如实保留缺口；提出替代架构时先给出官方直连影响、容量/辅助请求验证和恢复方案。历史隔离统一路由的成功不代替当前直接 provider 的验收。

### 4. 搜索来源与当前任务正确性

保留正常搜索配置。Web 的 `web_page_auto_v1` 只证明适配路径；2026-09-26 一条独立 GPT-6 Pro/max CLI 样例完成了网页搜索、绑定来源和最终回复，官方帮助页内容也支持该结论。其他问题、型号和 Desktop 主窗口仍须分别验收。GLM-5.3 官方 hosted 搜索、GLM-5.3 Flash 的 Codex 搜索和 DeepSeek 的端点能力分开，依据[在线模型证据](../../api/docs/official-online-models.md)。

验收：新问题指定明确目标来源，检查实际回答和来源内容；同时确认无额外 Codex 搜索执行。必须读完完整索引上下文，实际工具处理当前请求。只返回链接、读取所有页面或 HTTP 200 都不能代替这些检查。旧 citation/context 失败不重试。

## 变更与交付顺序

1. 用当前源码、保存登记、准确进程及既有证据确定缺口，避免重新实现已完成能力。
2. 完成一个明确行为修改后运行相关边界检查；部署前按范围做跨层回归与发布审计。
3. 部署核对空闲状态、源代码代次、保存原件及恢复路径；不知道是否执行过的操作不重复。
4. 用已授权的新测试验证实际行为，分别记录源码、隔离、本机部署与主窗口证据。
5. 将稳定经验写入当前指南，日期、失败与一次性 workaround 归入历史。最终按用户实际少做的步骤报告，不用测试数量代表全部产品完成。
