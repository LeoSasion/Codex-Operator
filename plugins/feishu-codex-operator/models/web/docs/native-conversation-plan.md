## 所有者确定的目标

2026-09-22 自动任务登记补丁：针对原生空摘要 paginated 任务的目录漏项，新增准确 UUID、
默认原生存储和未归档索引的一次只读核验，避免已创建任务因列表不可见而无法登记。
源码实机核验已确认现有任务可用，未改绑定、历史或原生配置；部署及回归记录见
[自动任务登记](../../../channels/feishu/docs/automatic-task-provisioning.md)。新用户首次
创建全链路及 `/init` 空摘要任务可见性仍分别待验，没有采用新的参考项目代码。

Chat On Steroids 是首要研究参考。衡量标准是整个 Codex 原生对话是否更流畅、更少点击、
更少配置、更少弹出辅助窗口。其他四个参考冷置，只有明确必要的缺口才重新查阅；
保留历史引用和许可证。大幅内部重构可以考虑，大方向变动先汇报计划再实施。

日常入口仍是原生 Codex 任务。用户明确不需要上游独立工作界面、浏览器伴随扩展产品、
Goal/Loop 或另一套多智能体编排。登录、人工验证、权限审批由应有的原生界面处理；
减少交互的目标针对重复和不必要的步骤，不把这些决定隐藏起来。

## 现有基础与待确认缺口

- 已有保存配置、固定连接、隐藏浏览器进程及取消后确认空闲再接纳新输入的实现。
  先复用这些能力，避免将已经实现的功能重新包装为本轮成果。
- [页面宿主](../../../scripts/web_browser_host.cjs) 在 `runCurrentPage` 开始时准备新页面，
  再选择模型和准确连接；第一轮承担页面加载开销。`loadFreshPage` 已支持已准备页面复用，
  也对已完成页面使用原生新聊天动作。新的预热方案需要明确准备内容、失效与消费条件。
- [快速开始](../../../QUICKSTART.md) 明确新任务接入独立 Web provider 仍需助手协助。
  provider 登记、任务绑定、菜单可见与请求实际去向目前仍是不同验证点。
- 历史记录有冷页加载失败、打开辅助页后新请求成功的案例。它提示后台准备值得研究，
  不能证明“显示窗口”就是修复，亦不能用新请求成功改判原失败。
- 初始受限环境的状态检查返回部分不可确认；后续授权读取核实是检查环境的访问限制，
  保存配置完整、后台 ready/idle。首批改动据此补齐原因区分；不能用初始错误要求重配，
  也不能据此停止或替换服务。

## 分阶段实施方案

### 第一阶段：保存一次，后续准确复用

用户收益：已经配好的登录和连接直接使用；升级后只处理实际变化的部分。

先核对统一管理入口的路径、登记和状态获取，准确区分入口不可检查、后台未启动、连接
未就绪和需要人工登录。在现有服务管理器及固定连接中补齐缺失的状态，不能用“请重配”
掩盖诊断失败。对工具声明建立完整变更判定，复用准确 app 身份；读回已经一致时无需
刷新。维护仅在准确空闲实例内发生，保留一次操作记录与未知状态。

验收：重复检查和无关配置变化不创建新连接；声明未变时零刷新点击；声明变化能定位到
具体维护步骤；账号、授权、固定连接仍复用。先隔离验证，再记录实际 UI 交互次数。

### 第二阶段：后台就绪后再承接原生对话

用户收益：首轮少等页面初始化，连续对话和停止后的新输入不要求反复打开辅助窗口。

拟在现有 Electron 宿主与服务管理器内整理“进程存在、空白页面已准备、模型与连接就绪、
正在执行、需要人工协助”的状态。只在已授权的启动/准备动作中做一次隐藏准备，不发送
模型请求；普通只读 status 不触发准备。保留完整原生输入、工具结果及旧失败记录。

这会改变页面准备时机，属于须先汇报的架构方向。先验证当前宿主能够维持后台渲染和
准确状态，再决定是否拆分准备与请求执行模块。未知启动、已失败请求和已取消输入不能
通过预热恢复或重放。已完成页面的只读检查也必须有明确保留策略。

验收：分别测量冷启动与复用时的本地准备耗时；正常路径不抢焦点、不弹辅助窗口；同一
原生任务连续三轮和停止后新输入保持历史与工具身份；登录失效时准确引导当前一步。
所有数字由新样例实测，不推断上游生成时间或承诺首字耗时。

### 第三阶段：原生任务中的模型接入与选择

用户收益：新任务和模型切换尽可能复用已有设置，减少助手协调多个入口的次数。

2026-09-21 已只读复核 Desktop 26.915.4065.0 / CLI 0.155.0-alpha.9.2：
原生 `thread/settings/update`、`turn/start` 仍只允许更改模型名称等设置，未提供
provider 切换字段，`model/list` 也没有逐项 provider 路由。Desktop 当前设置更新
使用该接口；不能将这些字段解释为跨提供方选择已打通。本次未改原生任务或路由，
菜单接入和任务实际请求去向继续分开验收。

先确认当前 Desktop 版本支持的 provider/任务配置接口与真实菜单行为，再比较两条路线：
继续独立 provider 并整合现有接入步骤；或在确有必要且完成原生兼容验证后改造统一路由。
当前官方直连和 native-only 状态是基线，不能凭上游 RFC、目录可见或历史隔离成功直接
恢复全局路由。若需要替换浏览器承载方式、全局路由或任务绑定机制，另报具体改动、
迁移/恢复步骤和验收范围后实施。

验收：新任务接入、同任务模型选择、实际请求去向、历史接续、工具读改测和原生审批
分别检查；官方原生辅助请求与容量边界继续单独验证。只读菜单或元数据不算执行通过。

## 验证与交付顺序

1. 先记录现状：首次配置动作、日常重复动作、辅助窗口次数、本地准备耗时及失败类别。
2. 按最小可验证改动实施；相关模块检查通过后再扩大到跨层回归，不重复无关测试。
3. 部署前准确核对服务、未完成请求、源码代次与保存状态；有界替换时保留原件和恢复路径。
4. 用新的原生任务样例验证启动、连续对话、取消、失联、重新打开和升级复用；旧失败不重发。
5. 分别报告源码完成、隔离检查、部署和主窗口验收，最终以用户实际少做了哪些步骤衡量。

初始交付为参考策略、研究计划及规则同步；随后所有者同意的首批代码与验证见本页开头。
