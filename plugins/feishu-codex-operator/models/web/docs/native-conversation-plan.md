早先多条原生样例执行只读命令后，因 250 项同身份内部工具定义改变而拒绝配对结果。9 月 27 日的新字段诊断确认另一条样例仅有 24 项叶子工具说明改变，参数、权限、身份与顺序未变。现在仅允许更新从未读取过的工具 schema 中的说明；目录已发布的首个读取 key 保持，完整新说明按原有边界重新分页，结果身份和历史全部校验后才原子发布。已读/部分已读定义及其他字段仍拒绝，具体规则见[项目记忆](native-web-experience.md)。新的原生只读任务在实际更新 250 项未读说明后完成结果和最终回复；同任务的独立温度案例也完成读改测。更新来源尚未确认，不能把这种兼容扩展为任意目录变化，旧失败保持原判。

与当时核对的本机版本号对应的 [Codex 官方源码](https://github.com/openai/codex/tree/rust-v0.155.0-alpha.16.4) 表明，顶层工具声明[每步重建](https://github.com/openai/codex/blob/3853cf0c49daadcacaacceb2cbb732f512eaacdb/codex-rs/core/src/tools/spec_plan.rs#L532-L569)，同一 MCP binding 的工具定义由已建好的 spec 复用；`tool_search` 的延迟加载结果进入[输入历史](https://github.com/openai/codex/blob/3853cf0c49daadcacaacceb2cbb732f512eaacdb/codex-rs/core/src/tools/context.rs#L208-L245)，不能据此解释顶层声明改写。认证、环境或插件状态变化可能触发[绑定刷新](https://github.com/openai/codex/blob/3853cf0c49daadcacaacceb2cbb732f512eaacdb/codex-rs/core/src/session/mcp.rs#L175-L253)，但本例没有这类事件证据，公开源码也未证明与本机二进制字节完全相同。未读说明兼容来自实际字段和阅读状态校验，不依赖对生成原因的猜测。

2026-09-27 回查找到了 9 月 18 日真实 Desktop G1 的原始成功回执（两次命令、精确修改、五项测试）及目录整理前的 9 月 20 日发布源码。在本次修复前，该发布快照与工作区的 `_accept_result`、`WebModelProtocol.__init__` 语法树一致，工具适配器的函数和类也一致；它不是 G1 当时全部源码的逐字节证明，但排除了这几处逻辑在后续目录整理中被改写。原始证据与失败记录仍保留；参考比较见[实现来源](web-background-sources.md)，测试范围见[发布审计](../../../development/docs/release-audit.md)。

### 3. 原生任务入口与模型选择

2026-09-28 再核对了 [codex-grok-bridge 的固定提交](https://github.com/deximple/codex-grok-bridge/tree/d6ff3ee991a7360f227b80f065589ae5d7453b77)（MIT；仅研究设计，未复制代码）。当前 CLI 的隔离实验确认：空闲任务可卸载后以同一 UUID、另一 provider 恢复，并保留历史和权限；但所有者明确指出这条早已排除的转接路线无法满足 **Codex Desktop 原生显示执行过程** 的要求。已停止包装层实现，不能再把“UUID 相同”当作原生体验验收。后续只考虑由 Desktop 自己持有并显示任务与工具过程的入口；任何统一路由恢复仍需先通过原生 413、搜索/图片/语音辅助、WebSocket、权限和主窗口回退验收，不能凭隔离目录显示启用。

当前 Desktop 26.924.2738.0 的普通新任务不提供逐任务 provider 选择，运行中的 0.158.0-alpha.2.1 App Server 也没有从主窗口接收此选择；[对应版本的配置加载器](https://github.com/openai/codex/blob/rust-v0.158.0-alpha.2.1/codex-rs/config/src/loader/mod.rs)禁止项目配置覆盖 provider/profile。因此单靠项目配置或另一个 App Server 为新任务绑定统一 provider，不能称为主窗口原生方案。统一 `openai_base_url` 候选若恢复，会影响官方原生流量。[当前版官方语音实现](https://raw.githubusercontent.com/openai/codex/rust-v0.158.0-alpha.2.1/codex-rs/core/src/realtime_conversation.rs#L1222-L1246)把 WebSocket 和 WebRTC call 当作两条独立路径；[两个覆盖字段](https://github.com/openai/codex/blob/rust-v0.158.0-alpha.2.1/codex-rs/config/src/config_toml.rs#L2832-L2856)都标为实验性。[参考项目](https://github.com/miuuyy/codex-chatgpt-web/blob/fa2d2c6c24926078b46eedb2186f69f2e8d548d7/docs/architecture.md#L262-L273)也将语音留在官方地址。本项目已为新的受管激活块分别固定两条官方语音地址，并验证精确撤回及旧块恢复；旧块缺任一保护时不再被视作语音安全。真实 Desktop 语音通话尚未验收，不能以普通文字回合代替。

上下文窗口按实际选中的模型及端点逐项核实；当前 Web 预算与 Desktop 实测值的差别只在[项目记忆](native-web-experience.md#operational-rules)维护。来源不明时保留未验证状态，不用猜测值解决长上下文失败。
[codex-chatgpt-web 的固定提交架构说明](https://github.com/miuuyy/codex-chatgpt-web/blob/fa2d2c6c24926078b46eedb2186f69f2e8d548d7/docs/architecture.md) 在这个具体缺口上区分 Instant 与其他档位的上下文预算，并在合并多个推理档位前检查预算一致；这是可借鉴的校验方式，不是本账号各网页型号的容量证据。本项目未复制其代码或数值。

9 月 29 日统一入口验收前的基线是官方直连加独立 Web provider，专用 Web 任务由助手配置。CLI 0.155.0-alpha.16.3 的合成检查证明：新任务可绑定未列于主 `model/list` 的准确 Web provider；首轮落盘后新进程可恢复该绑定。新进程也能显式切换提供方；同进程已加载任务的恢复/设置更新探测仍把请求送到原提供方。因此菜单出现、配置返回成功和实际去向必须分别核对。9 月 30 日同一统一 provider 内的原生/Web 切换证据见本文开头，不能与这组旧的跨 provider 检查混用。

2026-09-29 的隔离基线在 0.158 CLI 验证一个同一 provider 的候选：官方条目与 Web 条目同列于 `model/list`，原生任务由官方型号切到 Web 型号后，新输入抵达所选端点；当时 Web 后端是本机模拟。另一个使用合成 API key 的候选通过准确后端路径转发原生搜索、以动态 `model_catalog_url` 读取目录，并把 413 限为单次请求；内置官方 provider 在同一隔离 413 案例中重复发送。一次仅调用 `model/list` 的登录态 CLI 探测还确认自定义 provider 的目录请求带有认证，但它意外改写本机模型缓存；后来缓存已无合成条目，原始字节一致性无法证明，不重复做无快照的账号目录探测。[一次性配置候选](../../common/docs/unified-picker-candidate.md)验证了生成的 TOML 可被读取并列出合成的官方与 Web 条目。这组隔离检查未启用真实 Desktop；9 月 30 日后续主窗口验收及恢复后的当前状态以上文为准。代码与边界见[路由合同](../../common/docs/model-router.md#native-picker-candidate-2026-09-29)。

2026-09-27 已在 CLI 0.158.0-alpha.2.1 上修复旧任务缓存地址这一维护缺口：原生工具归档并恢复同一空闲任务后，全新的文件读取请求完成实际配对调用和准确最终回复，未重启 Desktop、改写全局配置或重建任务。恢复工具曾返回加载错误，但只读核验确认它已经解除归档；未重复恢复操作。具体操作与停止条件只维护在[任务重载](native-web-experience.md#reload-an-idle-web-task)。此结果不改变上述跨 provider 切换仍待验证的结论。

已有专用任务在助手任务工具转交下完成过文本接续；该转交不是普通输入框。9 月 28 日又完成了当前 Web-only 搜索配置下的主窗口打开、普通输入和三轮接续，详见上面的连续任务记录。停止按钮与任务工具接续的后续实测见上文；普通输入框的整条停止链路及受支持的模型选择入口仍需分别验证。不能为了跨 provider 切换自动重启 Desktop、改既有任务历史或恢复全局路由。

验收：新任务接入、同任务选择、实际请求去向、历史接续、读改测和原生审批各有准确证据。若原生接口仍不支持切换，如实保留缺口；提出替代架构时先给出官方直连影响、容量/辅助请求验证和恢复方案。历史隔离统一路由的成功不代替当前直接 provider 的验收。

### 4. 搜索来源与当前任务正确性

保留正常搜索配置。Web 的 `web_page_auto_v1` 只证明适配路径；2026-09-26 一条独立 GPT-6 Pro/max CLI 样例完成了网页搜索、绑定来源和最终回复，官方帮助页内容也支持该结论。其他问题、型号和 Desktop 主窗口仍须分别验收。GLM-5.3 官方 hosted 搜索、GLM-5.3 Flash 的 Codex 搜索和 DeepSeek 的端点能力分开，依据[在线模型证据](../../api/docs/official-online-models.md)。

验收：新问题指定明确目标来源，检查实际回答和来源内容；同时确认无额外 Codex 搜索执行。必须读完完整索引上下文，实际工具处理当前请求。只返回链接、读取所有页面或 HTTP 200 都不能代替这些检查。旧 citation/context 失败不重试。

## 变更与交付顺序

1. 用当前源码、保存登记、准确进程及既有证据确定缺口，避免重新实现已完成能力。
2. 完成一个明确行为修改后运行相关边界检查；部署前按范围做跨层回归与发布审计。
3. 部署核对空闲状态、源代码代次、保存原件及恢复路径；不知道是否执行过的操作不重复。
4. 用已授权的新测试验证实际行为，分别记录源码、隔离、本机部署与主窗口证据。
5. 将稳定经验写入当前指南，日期、失败与一次性 workaround 归入历史。最终按用户实际少做的步骤报告，不用测试数量代表全部产品完成。
